# Кредитная анкета и данные бизнеса

FastAPI + Python 3.11+. Бэкенд задаёт вопросы по переданным дереву и
`credit_dialog.py` от 23.10.2026, сохраняет ответы в SQLite и возвращает
общий JSON: данные компании, параметры финансирования, финансовые ответы,
предварительные кандидаты и причины уточнений.

Активны только бесплатные публичные **ЕГРЮЛ/ЕГРИП, «Прозрачный бизнес» и ГИР БО**.
КАД, ФССП, Федресурс, ЕФРСБ и реестр залогов отключены: обычные запросы их не
вызывают и не добавляют в JSON. Старые адаптеры оставлены для совместимости и
проверки сохранённых fixtures. Аккаунтов, ключей и платных сервисов нет.

## Запуск

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -e .
.\.venv\Scripts\python.exe -m uvicorn fns_parser.api:app --host 127.0.0.1 --port 8000
```

Если окружения нет: `py -3.12 -m venv .venv`. Для Linux/macOS используется
`.venv/bin/python`. [Swagger](http://127.0.0.1:8000/docs),
[OpenAPI](http://127.0.0.1:8000/openapi.json).

Сервер пока предназначен для локального MVP: без пользователей и авторизации.
ID сессии и задания дают доступ к соответствующим данным. Общего списка сессий
нет. Работайте с **одним процессом Uvicorn**: анкеты сохраняются в SQLite, но
фоновые задания парсера пока находятся в памяти процесса.

## Диалог и единый JSON

| Метод и путь | Назначение |
|---|---|
| `POST /api/v1/credit/sessions` | Создать анкету, получить Q01 |
| `GET /api/v1/credit/sessions/{id}` | Текущий общий JSON и следующий вопрос |
| `POST /api/v1/credit/sessions/{id}/answers` | Ответить или исправить ранее заданный ответ |
| `POST /api/v1/credit/sessions/{id}/registry` | Присоединить результат завершённого задания парсера |
| `GET /api/v1/credit/sessions/{id}/result` | Итоговый общий JSON; 409, пока есть вопросы |
| `DELETE /api/v1/credit/sessions/{id}?revision=N` | Удалить анкету |

Создание не требует тела. Пример ответа на первый вопрос:

```json
{
  "revision": 0,
  "question_id": "knowledge",
  "value": "no"
}
```

В `question_id` запроса нужно передавать **`next_question.id`**, например
`loan_balance`. Поле `next_question.question_id` содержит номер из дерева,
например `Q09`: один номер может включать несколько разных полей.
`next_question` также содержит текст, тип, варианты и ограничения.

Для выбора используйте `options[].value`, для чисел — JSON-число, для даты —
`YYYY-MM-DD`. `null` означает «не знаю», если `allow_unknown=true`.
У выбора с вариантом `unknown` допустимы и `null`, и строка `unknown`;
в общем JSON оба превращаются в `null`. Числовой ноль сохраняется как ноль.
ИНН проверяется по длине, форме бизнеса и контрольной цифре.

Каждый успешный запрос изменения возвращает новую `revision`. Устаревшая
версия даёт HTTP 409 `revision_conflict`; получите свежую сессию перед повтором.
Нельзя отвечать на не заданный вопрос. При **изменении** предыдущего ответа
все последующие ответы удаляются и ветка строится заново. Повтор того же
значения сохраняет следующие ответы. Если после исправления ИНН исчез или
сменился, связанный результат парсера также удаляется из анкеты.

Структура ответа `credit-application-1.0`:

| Поле | Содержимое |
|---|---|
| `session_id`, `revision`, даты | Сессия и версия |
| `state` | `collecting` или `ready` — вопросы закончились |
| `next_question` | Следующий вопрос либо `null` |
| `data.borrower` | Форма и регистрация бизнеса, сведения ИП |
| `data.company` | ИНН, выбранный ОГРН, компактные карточки регистраций, статусы и даты источников |
| `data.financing` | Цель, сумма, срок, дата, схема выдачи, объект/контракт |
| `data.existing_loan` | Заменяемый кредит при рефинансировании |
| `data.bank` | Счёт, персональное предложение и подписка |
| `data.security` | Залог, поручительство и собственные средства |
| `data.financials` | Ответы о сезонности, месячной выручке, остатке и платежах |
| `answer_states` | Статус каждого заполненного поля: `provided`, `unknown`, `derived`, `registry` |
| `field_sources` | Источник полей анкеты, взятых из парсера |
| `conflicts` | Расхождения: ответ пользователя и выбранное значение реестра |
| `recommendation` | `R01` / `R02` / `R03`, кандидаты, причины и непроверенные условия |

Денежные поля с `_rub` — рубли, `_monthly_rub` — рубли в месяц. Если ключа
нет в `answer_states`, вопрос ещё не задан либо пропущен по ветке.
Так, при `seasonal=no` Q29–Q30 не задаются, а выручка и остаток остаются `null`.
Производное `reuse=yes` при регулярной закупке помечается `derived`.

## Как присоединить парсер по ИНН / ОГРН

После получения ИНН в Q13 запустите задание существующего парсера (можно
передать точный ОГРН / ОГРНИП этой компании):

```http
POST /api/v1/jobs
Content-Type: application/json

{"identifier":"1124028002273","enrich":true}
```

Ответ — HTTP 202 с `job_id`. Опросите `GET /api/v1/jobs/{job_id}` до
`state=completed`, затем присоедините результат к анкете:

```http
POST /api/v1/credit/sessions/{session_id}/registry
Content-Type: application/json

{"revision":12,"job_id":"JOB_ID","selected_ogrn":"1124028002273"}
```

`revision` берётся из последнего ответа анкеты, а не из задания. Анкета
принимает **серверный** результат задания; произвольный JSON от клиента нельзя
объявить данными ФНС. ИНН результата должен совпадать с ИНН анкеты. При поиске
по ОГРН проверяется связь найденного ОГРН с этим ИНН.

Единственная регистрация выбирается автоматически. При нескольких
регистрациях ИП все карточки сохраняются; укажите нужный `selected_ogrn`.
Без выбора сведения разных ОГРНИП не смешиваются, итог содержит уточнение.
Неполный/ошибочный результат можно сохранить: статус ошибки виден в JSON и не
превращается в подтверждённый ноль. Подтверждённые поля сохраняют свои значения.
После присоединения копия результата находится в SQLite и переживает
перезапуск даже после истечения срока хранения задания.

## Приоритет данных

Для одинаковых по смыслу полей приоритет такой:

1. Подтверждённые непустые сведения выбранной регистрации из парсера.
2. Ответ пользователя, если подходящего подтверждённого значения нет.
3. `null`, если значения нет ни в одном источнике.

Сейчас пересечения с вопросами — ИНН, форма и текущий статус регистрации.
Форма ООО определяется по явному названию организационно-правовой формы;
неизвестная форма не угадывается. Статус регистрации определяется по явному
статусу деятельности или дате прекращения/недействительности регистрации.
Сам факт старой регистрации не доказывает, что бизнес действует сейчас.

Выбранные значения используются **и в итоговом JSON, и при подборе продукта**.
Исходный ответ остаётся в SQLite; при расхождении он также есть в `conflicts`.
Ошибка источника или `no_data` не затирает ответ пользователя.
Остальные реквизиты (название, адрес, ОКВЭД, капитал, руководители, учредители,
сотрудники, отчётность) берутся непосредственно из `data.company.entities`.

Показатели с разным смыслом или периодом не конфликтуют:

- годовая выручка ГИР БО не заменяет среднюю месячную выручку пользователя;
- доход по данным ПБ не считается выручкой;
- заёмные средства в балансе не заменяют ежемесячные платежи;
- налоговая задолженность на опубликованную дату не доказывает отсутствие
  текущих кредитных просрочек.

Все исходные периоды и даты остаются рядом с показателями. Пересчёта
годовой выручки в месячную делением на 12 нет.

## Правила подбора

Используется снимок предоставленной карты от **23.10.2026**, без автоматического
обновления банковских условий. `is_bank_decision=false`: это предварительный
подбор типа продукта. Пороги скоринга, ставка и одобрение не вычисляются.

- `R01` — есть предварительный кандидат; проверки заявки остаются впереди.
- `R02` — требуется уточнение, подтверждение условий или отдельная программа.
- `R03` — все рассмотренные варианты исключены по заданным правилам.

`state=ready` означает завершение вопросов и не означает одобрение кредита.
Без подтверждённой карточки по Q13 результат для бизнеса — R02.
Овердрафт проверяется по 60/90 дням; 6 месяцев линии считаются календарно.
P11 и личные программы не становятся автоматически подтверждёнными.
Просрочки сами по себе не вызывают отказ, удалённые Q14–Q16 и Q38–Q41 не задаются.
По PDF добавлены детали личных просрочек Q37, которых не было в CLI.
Заявка R04, документы, согласия и решение банка — следующий этап реализации.

## Парсер отдельно

```powershell
.\.venv\Scripts\python.exe -m fns_parser 4028051108 -o output/company.json
.\.venv\Scripts\python.exe -m fns_parser 1124028002273 --full -o output/full.json
.\.venv\Scripts\python.exe -m fns_parser --from-json output/full.json -o output/compact.json
```

`--basic` отключает ГИР БО; `--max-pages` (1–10, по умолчанию 3) ограничивает
поиск ГИР БО. `--download-dir` задаёт каталог PDF. Краткая схема —
`compact-1.0`, полная — `1.0`. Полный JSON содержит исходные поля и локальные
пути PDF. Преобразование старого файла `--from-json` сохраняет его источники;
новые сетевые запросы обращаются только к трём активным источникам.

| HTTP API | Назначение |
|---|---|
| `GET /api/v1/companies/{identifier}` | Синхронный краткий JSON |
| `?full=true` | Полный JSON |
| `?enrich=false` | Только ЕГРЮЛ/ЕГРИП и ПБ |
| `POST /api/v1/jobs` | Фоновый сбор |
| `GET /api/v1/jobs/{job_id}` | Статус и результат |
| `DELETE /api/v1/jobs/{job_id}` | Отмена |
| `GET /health` | Проверка API без обращения к ФНС |

Сбор может занять больше минуты. Неуспех источника даёт `partial`, а не
пустые подтверждённые данные. Неизвестные поля краткой карточки не добавляются
искусственно. У одного ИНН могут быть несколько регистраций ИП.
Прежняя страница `/captcha` позволяет запускать задания и смотреть JSON.
Механизм ручной капчи оставлен в коде, но отключённые источники не вызываются.

## Настройки и ошибки

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CREDIT_DB_PATH` | `data/credit.sqlite3` | Сохранённые анкеты |
| `FNS_DOWNLOAD_DIR` | `data/extracts` | PDF-выписки |
| `FNS_TIMEOUT` | `20` | Таймаут одного HTTP-запроса источника |
| `FNS_WAIT_TIMEOUT` | `60` | Ожидание каждого результата ФНС |
| `FNS_MAX_CONCURRENT` | `2` | Одновременные задания / синхронные запросы |
| `FNS_CORS_ORIGINS` | пусто | Разрешённые адреса фронтенда через запятую |
| `FNS_JOB_RETENTION` | `900` | Хранение завершённого задания, секунды |
| `FNS_MAX_JOBS` | `32` | Максимум заданий в памяти |
| `FNS_CAPTCHA_TIMEOUT` | `120` | Ожидание в сохранённом механизме ручной проверки |

Все ответы анкеты и задания имеют `Cache-Control: no-store`.
Анкеты хранятся до явного DELETE. Ошибки API возвращаются в формате
`{"status":"error","error":{"code":"...","message":"..."}}`.
404 — неизвестная сессия/задание; 409 — конфликт версии, незавершённая анкета,
неподходящий вопрос или несовпадение компании; 422 — неверный ответ/идентификатор;
503 — все слоты парсера заняты. У синхронного парсера 404 также означает
`not_found`, 502 — ошибку источников с подробностями в `sources`.

## Проверка

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -v
```

Тесты проверяют все цели, ветвление, ноль/неизвестное/пропущенный вопрос,
возобновление сессий, правки ответов, конкурирующие запросы, приоритет реестра,
конфликты, выбор регистрации, календарные сроки и отключение пяти источников.
Сетевые ответы в тестах подменены; реальные примеры сохраняются отдельно в `output/`.

Проверка текущей версии: **83 теста прошли**. Через запущенный API выполнен
запрос по ОГРН `1124028002273`: ЕГРЮЛ, ПБ и ГИР БО вернули `ok`.
`output/credit-example.json` содержит реальную карточку этого юрлица и
**демонстрационные** ответы анкеты: сумма, платежи, просрочки и остальные
ответы не являются установленными фактами о компании. В примере ошибочный
ответ `other_legal` заменён на `ooo` из парсера с записью в `conflicts`.
Отдельный ответ источников сохранён в `output/credit-registry-live.json`.

## Пул из 10 000 компаний для скоринга

```powershell
.\.venv\Scripts\python.exe -u -X utf8 -m fns_parser.dataset_pool
.\.venv\Scripts\python.exe -X utf8 -m unittest tests.test_dataset_pool -v
```

Сборщик создаёт `output/scoring_pool_10000/companies.jsonl` — ровно 10 000
уникальных юрлиц с ИНН, ОГРН, названием, регионом, основным ОКВЭД, категорией
МСП, численностью сотрудников и, при наличии записи, годовыми доходами и
расходами в рублях. `identifiers.json` содержит только пары ИНН/ОГРН,
`examples.json` — по одному примеру каждого финансового случая,
`manifest.json` — даты, URL источников, контрольные суммы, фактические
распределения и ограничения выборки. Эти файлы не содержат ответов анкеты.
Если основной ОКВЭД есть только в отчётном разделе, отрасль определяется по
`reported_main_okved`; использованное поле записано в `industry_bucket_basis`.
Оба исходных поля ОКВЭД сохраняются отдельно.

Источники бесплатны и не требуют регистрации:
[реестр МСП ФНС](https://www.nalog.gov.ru/opendata/7707329152-rsmp/), срез
10.10.2026, и [доходы/расходы ФНС](https://www.nalog.gov.ru/opendata/7707329152-revexp/),
публикация 25.09.2026. Отчётный период сохраняется отдельно от даты публикации.
Первый источник даёт основу выборки, второй позволяет отбирать разные финансовые
ситуации. Список трёх источников существующего API компании не меняется.

Из ZIP реестра выбираются 200 случайных XML с фиксированным seed; скачиваются
только их диапазоны байтов. Из них берутся юрлица с корректными контрольными
цифрами ИНН/ОГРН. Компании с отрицательными суммами в финансовом источнике
исключаются до выяснения смысла этих значений; знаки не меняются автоматически.
Внутри каждой финансовой группы отбор чередует сочетания
региона, отрасли и категории МСП. План: доходы выше расходов — 5000, расходы
выше доходов — 2500, нулевые доходы — 1000, равные положительные доходы и
расходы — 500, нет финансовой записи в выпуске — 1000. Если кандидатов в группе
недостаточно, остаток добирается из остальных; фактические числа отражает manifest.
Скачанное кешируется в `data/scoring_pool_cache/`; повторный запуск использует кеш.
Версии источников зафиксированы в коде, поэтому это воспроизводимый срез,
а не автоматическое обновление до последней публикации.

Это пул кандидатов и исходных признаков, **не размеченная обучающая выборка
кредитных дефолтов**. `credit_default_90dpd_12m=null`: ни доходы/расходы,
ни отсутствие записи не подтверждают погашение или просрочку кредита.
Для такой цели нужны реальные исходы кредитов и даты наблюдения. Разность
доходов и расходов этого набора не называется выручкой или чистой прибылью.
`msp_included_on` — дата включения в МСП, не дата регистрации юрлица;
нулевая численность отличается от неизвестной. Категории МСП и признак нового
бизнеса сохранены кодами источника.

Текущий реестр не охватывает весь бизнес и создаёт риск смещения к выжившим
компаниям при историческом анализе. Выбор XML является кластерной выборкой;
балансировка финансовых групп, регионов и отраслей не воспроизводит распределение
заёмщиков банка и не подходит сама по себе для калибровки вероятности дефолта.
Признаки для модели должны быть доступны на дату решения по кредиту. Связанные
компании и повторные наблюдения одного ИНН нельзя разносить между train/test;
связи групп здесь ещё не собраны. Все 10 000 выписок ЕГРЮЛ, карточек ПБ и отчётов
ГИР БО пока не скачаны индивидуально: `parser_enrichment_status=pending`.

## Пакетный парсинг и CSV для обучения

Запуск из корня проекта для всех 10 000 компаний:

```powershell
.\.venv\Scripts\python.exe -u -X utf8 -m fns_parser.batch_training run
```

По умолчанию берётся `output/scoring_pool_10000/identifiers.json`, результат
сохраняется в `output/scoring_training/`. Для каждой компании вызывается наш
`parse_company(full=True, enrich=True)`: ЕГРЮЛ/ЕГРИП, «Прозрачный бизнес», ГИР БО.
Сбор идёт последовательно с паузой в одну секунду между компаниями; максимум
две попытки на компанию за запуск. `--input` принимает JSON со списком ИНН/ОГРН
или объектов `inn`/`ogrn`, JSONL пула либо CSV с колонками `inn`/`ogrn`
или `meta_inn`/`meta_ogrn`. Идентификаторы должны быть строками с ведущими нулями.
При наличии ОГРН запрос идёт по нему; возвращённый ИНН проверяется по входной паре.

Пробный запуск использует отдельный каталог, чтобы не смешивать разные когорты:

```powershell
.\.venv\Scripts\python.exe -u -X utf8 -m fns_parser.batch_training run --limit 2 --output output/scoring_training_smoke
```

Заголовок присланного `company_scoring_training_draft.csv` из 65 колонок
встроен в конвертер. Необязательный `--template "путь/к/файлу.csv"` проверяет
заголовок и сохраняет его порядок; значения из демонстрационной строки не копируются.
Колонки ответов анкеты и кредитных исходов остаются неизвестными, пока такие
данные не поступят из соответствующих источников. Этот сборщик получает только
сведения реестров и не присваивает компании ответы из примеров анкеты.

В каталоге результата:

| Файл / каталог | Содержимое |
|---|---|
| `raw/` | Полный JSON каждой попытки, включая сведения ГИР БО, не представленные в CSV-шаблоне |
| `extracts/` | Скачанные выписки PDF |
| `records/` | Прогресс по каждой компании и ссылка на выбранный результат |
| `dataset_raw.csv` | Все 65 колонок шаблона в исходном порядке, служебные поля и флаг `<поле>_missing` для каждого поля |
| `dataset.csv` | Категориальные признаки заменены one-hot колонками; метаданные и исходы сохранены отдельно от признаков |
| `features.csv` | Только числовая матрица признаков, в том же порядке строк, что `dataset.csv` |
| `encoder.json` | Категории, порядок колонок, список признаков и правила кодирования |
| `field_sources.jsonl` | Происхождение заполненных значений и ошибки преобразования |
| `report.json`, `run.json` | Количество строк, пропуски, статусы источников/попыток, причина остановки |

Правила пропусков применяются **до** заполнения нулями:

| Значение источника | Значение в CSV | `<поле>_missing` |
|---|---:|---:|
| `250000` | `250000` | `0` |
| Настоящий `0` | `0` | `0` |
| Поле отсутствует / `null` / некорректное число | `0` | `1` |

Категории кодируются колонками вида `entity_type__value_legal`,
`main_okved__value_71.12`. Символы названий категорий экранируются в именах колонок;
исходные названия записаны в `encoder.json`. При пропуске все индикаторы категории
равны нулю, а её общий `_missing=1`. Несколько одновременно указанных налоговых
режимов дают несколько единиц. Новая категория при использовании сохранённой
схемы даёт `__unseen=1`, `_missing=0`; колонки при этом не меняются.

Дата регистрации в числовой таблице — число дней с 1970-01-01, месячные периоды —
число месяцев с 1970-01. В `dataset_raw.csv` сохраняются ISO-даты.
`t0` — последний имеющийся год финансовых данных, `t1=t0-1`, `t2=t0-2`.
Отсутствующий год не сдвигает более старые показатели в соседнюю колонку.
Доходы/расходы/уплаченные налоги берутся из соответствующих полей ПБ в рублях;
выручка ГИР БО и годовые показатели не подставляются вместо другого показателя
или среднего денежного потока за шесть месяцев.

ИНН, ОГРН, названия, все `meta_*`, `outcome_*`, целевая переменная и их флаги
исключены из `features.csv`. Для неизвестного исхода
`target_default_12m=0`, **`target_default_12m_missing=1`**: такая строка не является
примером отсутствия дефолта. Для обучения с учителем нужно выбирать только
строки с `target_default_12m_missing == 0`; после одного публичного парсинга
таких строк нет. CSV хранит идентификаторы текстом, но при ручном импорте в Excel
следует также выбрать текстовый тип, чтобы Excel не убрал ведущие нули.

Каждая попытка сохраняется атомарно. Повтор той же команды использует уже
собранные результаты и продолжает необработанные компании. `Ctrl+C` сохраняет
прогресс и экспортирует текущую таблицу; необработанные строки явно отмечены
`meta_parser_status=not_processed`. При капче, ограничении частоты или доступа
сбор останавливается после сохранения текущего результата и причины в `run.json`.
После устранения причины можно повторить ошибки:

```powershell
.\.venv\Scripts\python.exe -u -X utf8 -m fns_parser.batch_training run --retry-failed
```

`--refresh` запрашивает все компании заново и сохраняет прежние JSON. Ошибка новой
попытки не заменяет более полный успешный результат. Дата выбранного среза остаётся
в `meta_features_as_of`; последний статус виден в `meta_last_attempt_status`.
Одновременная запись двух сборщиков в один каталог запрещена блокировкой ОС.
Код завершения `2` означает частичные данные / остановку источником, `130` —
прерывание пользователем, `1` — ошибку ввода/файлов. CSV при штатной остановке
источником или `Ctrl+C` сохраняются, включая строки без результата.

Пересборка таблиц из сохранённых результатов без сетевых запросов:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m fns_parser.batch_training export
.\.venv\Scripts\python.exe -X utf8 -m fns_parser.batch_training export --json output/credit-registry-live.json --output output/scoring_training_example
```

Для стабильного набора колонок на validation/inference передайте
`--encoder-schema "путь/к/train/encoder.json"` в `run` или `export`.
При подготовке модели словарь категорий нужно формировать на обучающей части,
а затем применять к проверочной. Даты и исходы кредитов требуют отдельной
проверки временного разделения: текущий срез реестра не описывает автоматически
состояние компании на историческую дату заявки.

Проверка нового сборщика: **16 тестов прошли**. Пробный живой запуск двух
компаний из пула завершился с `ok` у всех трёх источников; результаты находятся
в `output/scoring_training_smoke/`. Все 10 000 входных идентификаторов проверены,
полный сетевой прогон запускается командой выше.

```powershell
.\.venv\Scripts\python.exe -X utf8 -m unittest tests.test_training_batch -v
```

### Быстрый датасет: массовые выгрузки и добор

Сборка всех строк теперь доступна без ожидания 10 000 отдельных карточек.
Используются сохранённый пул МСП, доходы/расходы за 2025 год и три официальных
массовых набора ФНС: специальные налоговые режимы, уплаченные налоги и задолженность.
Паспорта и адреса выпусков проверены 24.10.2026. Архивы скачиваются один раз;
сохраняются SHA-256, XML-файл, идентификатор записи, дата публикации и дата среза.

```powershell
# Скачать массовые наборы и собрать таблицы (повторно используются файлы кеша).
.\.venv\Scripts\python.exe -u -X utf8 -m fns_parser.bulk_training --fetch

# Пересобрать только из локальных выгрузок и новых JSON индивидуального парсера.
.\.venv\Scripts\python.exe -u -X utf8 -m fns_parser.bulk_training

# Продолжить индивидуальный добор, сохранив прежние файлы и результаты.
.\.venv\Scripts\python.exe -u -X utf8 -m fns_parser.batch_training run --retry-failed --fast --no-girbo --delay 5
```

Основной результат — `output/scoring_training_bulk/`: `dataset_raw.csv`,
`dataset.csv`, `features.csv`, `encoder.json`, `field_sources.jsonl` и `report.json`.
`companies.jsonl` содержит объединённый краткий JSON каждой компании,
`enrichment_queue.json` — недостающие поля для добора. Исходные выписки и полные JSON
остаются в `output/scoring_training/`; состав и порядок 10 000 компаний сохранены.

`bulk_only` означает, что строка содержит массовые данные; `bulk_enriched` — что
добавлены данные индивидуального парсера. Эти статусы **не означают полноту выписки**.
Статусы индивидуальных источников и последней попытки сохранены отдельно.
Общая дата сборки не заменяет даты источников: они записаны в `data_dates`,
`bulk_evidence` и `field_sources.jsonl`.

Массовые данные дополняются сохранёнными данными парсера. Для имени и основного
ОКВЭД сохраняется индивидуальная карточка, если она уже есть; для кадровых,
налоговых и финансовых значений используются массовые записи и соответствующие
им периоды. История финансов объединяется по календарному году, затем строятся
`t0/t1/t2`. Отсутствие компании в списке задолженности не подтверждает нулевой долг;
отсутствие записи о спецрежиме не подтверждает ОСНО. Дата включения в МСП не
подставляется вместо даты регистрации. Кредитные исходы остаются неизвестными.

`--fast` запрашивает ЕГРЮЛ и ПБ параллельно для одной компании. Успешные ответы
источников из предыдущей попытки повторно используются до 6 часов с сохранением
исходных дат; для PDF проверяются наличие файла и хеш. Сбойный источник запрашивается
снова. `--refresh` начинает новый срез. Число компаний, обрабатываемых одновременно,
не увеличивается; капча и ограничения источника по-прежнему останавливают добор.
`--no-girbo` отключает новые обращения к ГИР БО, чьих показателей нет в 65 полях
шаблона. Сохранённые ранее результаты ГИР БО не удаляются.

Проверка массового сопоставления и заполнения пропусков:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m unittest tests.test_bulk_training tests.test_training_batch tests.test_parser tests.test_public_sources -v
```


### Капчи ФНС в FastAPI во время пакетного сбора

Откройте `http://127.0.0.1:8000/captcha/batch`. Страница автоматически показывает
капчи ЕГРЮЛ/ЕГРИП и «Прозрачного бизнеса» из текущего пакетного прогона.
Введите шесть цифр и нажмите «Продолжить сбор». Неверный ответ или кнопка
«Новая картинка» запрашивает новую картинку; допускается не более пяти ручных
попыток на остановившийся запрос. Платного или автоматического распознавания нет.

```powershell
.venv\Scripts\python.exe -m uvicorn fns_parser.api:app --host 127.0.0.1 --port 8000
.venv\Scripts\python.exe -u -X utf8 -m fns_parser.batch_training run --retry-failed --fast --no-girbo --delay 5 --manual-captcha --captcha-timeout 1800
```

Запускайте команды в отдельных терминалах из корня проекта. FastAPI и сборщик
используют общую очередь `data/captcha.sqlite3`; для другого пути задайте
одинаковый `FNS_CAPTCHA_DB` обоим процессам (или `--captcha-db` сборщику).
Это очередь процессов на одном сервере. Картинки доступны через FastAPI;
куки ФНС и её токены остаются в памяти сборщика. После ответа повторяется
остановившийся запрос, затем продолжается текущая компания и остальной пул.
Обновление страницы и перезапуск FastAPI не теряют очередь, пока сборщик жив.
При завершении самого сборщика сессия ФНС теряется: следующий запуск использует
сохранённые результаты и при необходимости получает новую капчу.

По умолчанию одна картинка ожидает ответа 30 минут (`--captcha-timeout`).
ФНС может отклонить уже устаревшую картинку — тогда появится новая.
Таймаут или «Остановить на этой компании» сохраняют частичные данные и
останавливают прогон; готовые JSON и PDF не перезаписываются.
Коды удаляются из активной очереди после передачи сборщику и не попадают в
датасет, ответы статуса или логи. Очередь убирает изображения и ответы при
истечении срока или отсутствии heartbeat сборщика более минуты.

API для интерфейса:
- `GET /api/v1/batch/captchas` — ожидающие капчи, источник, ИНН/ОГРН и срок ожидания;
- `GET /api/v1/batch/captchas/{id}/image` — изображение;
- `POST /api/v1/batch/captchas/{id}/answer` — `{"action":"answer","code":"123456"}`,
  `{"action":"refresh"}` или `{"action":"skip"}`. Число выше — пример формата, не код настоящей капчи.

`output/scoring_training/live.json` обновляется во время работы и ручного
ожидания. Pending-капча с живым PID и обновляемым `heartbeat_at` означает
ожидание человека, а не зависание. Монитор не должен перезапускать этот процесс.
Кнопка остановки требует явного последующего возобновления пользователем.
Обычные задания `POST /api/v1/jobs` и страница `/captcha` также поддерживают
ручные капчи ФНС. Синхронный GET компании по-прежнему возвращает частичный
результат, если для источника нужен ручной ввод.

### Историческая выборка компаний с банкротствами

`output/scoring_training_with_bankruptcies/` — отдельный объединённый экспорт:

`companies.jsonl` в корне нового экспорта содержит все строки с настоящими `null`

Источники:

  на сайте издательского архива [Пресса.рф](https://xn--80aj3aega.xn--p1ai/ru/magazines/kommersant/31-2015).

  должника, противоречивые события и неоднозначные даты исключаются.
* [RFSD](https://github.com/irlcode/RFSD), версия 3.1.0, авторы Sergey Bondarkov,
  Viktor Ledenev, Dmitry Skougarevskiy, [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).
  [Набор данных](https://huggingface.co/datasets/irlspbru/RFSD),
  [публикация авторов](https://doi.org/10.1038/s41597-025-05150-1).
  Используются разделы Росстата за 2013, 2017 и 2018 годы; ревизия закреплена
  в коде и манифестах. Данные преобразованы: отбор компаний и периодов,
  исключение восстановленных/скорректированных значений, перевод тысяч рублей в рубли.

```powershell

.venv\Scripts\python.exe -u -X utf8 -m fns_parser.bankruptcy_sources
.venv\Scripts\python.exe -u -X utf8 -m fns_parser.bankruptcy_training all --count 1000
```

Первый шаг требует около 1,6 ГБ для финансовых разделов; сохранённые файлы
проверяются по хешам и используются повторно. Платные выпуски без бесплатной
ссылки пропускаются. Сетевые ошибки останавливают загрузчик, сохранённые файлы
не теряются. Без новых сетевых запросов экспорт можно повторить командой:

```powershell
.venv\Scripts\python.exe -u -X utf8 -m fns_parser.bankruptcy_training build --count 1000
.venv\Scripts\python.exe -X utf8 -m unittest tests.test_bankruptcy_training tests.test_training_batch tests.test_bulk_training -q
```

В новых колонках `ras_*_t0_rub`, `ras_*_t1_rub`, `ras_*_t2_rub` записываются
14 бухгалтерских показателей: выручка, чистая прибыль, прибыль до налогообложения,
активы, внеоборотные и оборотные активы, запасы, дебиторская задолженность,
денежные средства, капитал, долгосрочные и краткосрочные обязательства,
краткосрочные заёмные средства, кредиторская задолженность. `t0` — последний
подходящий доступный год; `t1/t2` — предыдущие календарные годы, которые могут
отсутствовать. Выручка РСБУ не подставляется в `income_t0_raw` из данных ФНС.

**Границы использования.** Дата среза — 31 декабря года перед событием.
Используется отчётность за год не позднее чем за два года до события; требуется
совпадение ИНН и ОГРН, `filed=1`, `imputed=0`, `totals_adjustment=0`, `outlier=0`,
`financial=0` и минимум два известных значения из выручки, прибыли, активов,
капитала. Но RFSD хранит последние редакции и не сообщает точную дату первой
публикации или исправления отчёта. Поэтому период отчётности предшествует событию,
а доступность именно этих значений на дату среза **не подтверждена**:
`meta_point_in_time_verified=0`, `meta_bankruptcy_training_eligible=0`.
ОКВЭД RFSD также гармонизирован авторами базы, а не восстановлен по выписке на дату среза.
В старых выгрузках Росстата нули неотличимы от пропусков; RFSD переводит их в `NA`.
Мы сохраняем их неизвестными (`0` вместе с `_missing=1`), не восстанавливая
мнимые настоящие нули. Известные ненулевые значения и отрицательная прибыль сохраняются.

`target_bankruptcy_12m=1` означает опубликованное судебное событие банкротства
в следующем календарном году после даты среза. Это не метка просрочки банковского
кредита; `target_default_12m` остаётся неизвестной. Последующие отмены решений
и апелляции по всей выборке не проверены, действующий статус банкрота не утверждается.
Исходные 10 000 компаний остаются без метки банкротства, а не становятся классом 0.
По датам отчётов и заполненности полей легко различить две части набора: для
обучения и честной оценки скоринга нужны сопоставимая историческая контрольная
выборка и проверка доступности отчётов на дату прогноза. `features.csv` технически
закодирован, но весь объединённый файл не является готовой обучающей выборкой.
